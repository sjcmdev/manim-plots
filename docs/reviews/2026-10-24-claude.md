# Freeze review: 0.1 scope and architecture (Claude, 2026-10-24)

I read everything listed in section 1 of `docs/prompts/review-freeze-mvp1.md`, plus the
Manim 0.21.0 sources in `.venv` and the 0.22.0 sources in the uv cache. Experiments ran
outside the repository. Manim snippets ran from the scratchpad. PoC experiments ran against
a copy of `poc4/` in the scratchpad. Manim 0.22.0 was imported from the uv cache with `-B`,
so nothing was written there. Commands and outputs are in the appendix (E1–E21), and
findings cite them by number. Manim citations give the symbol first, then 0.21.0 lines,
unless a line says otherwise.

## 1. Verdict

**Freeze after the listed blockers.** The mechanism survives the version matrix. All 17
stack frames PoC 4 reads are byte-identical in 0.22.0, and 228 of 228 behavioural PoC 4
tests pass there (E19, E20). The problems are elsewhere: six contracts the freeze would lock
are undefined, or contradict D17 in ways the Manim corpus hits on its very first scene.

## 2. Freeze blockers

### Blocker 1. Plot functions: when they are evaluated, and on what

- **Problem.** F-918 and D21 make every plot function an always-dirty binding, re-sampled
  on every rendered frame (`docs/scope.md:217`, `docs/grill-log.md:584-586`,
  `PLAN.md:239-248`). F-704 (`docs/scope.md:173`) does not say whether the function is
  called once per sample or once on an array. Either reading breaks something.
- **Evidence.**
  - *Late binding.* Three `ax.plot(lambda x: k * np.sin(x))` built in a comprehension have
    y-extents `[2.0, 4.0, 6.0]` after construction and `[6.0, 6.0, 6.0]` after one
    `play(Create(...))` (E1, PoC 4 model). The first corpus scene, `CoordSysExample`
    (`coordinate_systems.py::CoordinateSystem` docstring, `:77-117`), builds 78 plots in
    such a loop. It comes out right only because it plays nothing. Manim samples once, in
    the constructor (`functions.py::ParametricFunction.generate_points`, `:174`). A range
    change re-samples (F-104) and collapses the plots the same way, with or without F-918.
  - *Call convention.* Manim calls the function once per sample unless `use_vectorized=True`
    (`functions.py::ParametricFunction.__init__`, `:114`; `generate_points`, `:174`). Two
    functions raise `ValueError` on an ndarray (E2): `lambda x: 1 if x > 0 else -1`, and the
    function of the corpus `ParametricCurveExample` (`:868`). The PoCs evaluate on arrays
    (`poc4/model.py:510-511`; `docs/poc3-stack-context.md:380-381`).
  - *Cost.* Calling per sample on the F-1001 workload (4 × 2 000) costs 1.1–1.7 ms p95 per
    frame. The vectorised call costs 0.013–0.028 ms (E3). PoC 4 already used 3.07 ms (affine)
    and 3.73 ms (bilinear) of the 4 ms gate with array calls
    (`docs/poc4-keyed-alignment.md:353-354`).
- **Fix.**
  - Sample at construction and on data-channel changes.
  - Re-sample on every frame only when the user asks for a live function, through a keyword
    or a parameter bound to a tracker.
  - Keep Manim's `use_vectorized=False` as the default, with array evaluation as the opt-in.
  - State the calling convention in F-1001's workload.
  - Add late binding to F-1008: every resample is still exposed to it.
- **Cost.** Text changes to F-704, F-918, F-1001 and D21's third bullet, plus one
  re-measurement of F-1001.

### Blocker 3. The leaf lifecycle has no state × event table, and the model fails cells nobody specified

- **Problem.** Finding 2 of the arch-crew review asks for this table. Section 5 builds it
  from PLAN rules 1-5, F-903…F-907, D19-D21 and `poc4/model.py`. Of 108 applicable cells,
  64 are undefined. Seven of those fail in the closest-to-production model or contradict
  PLAN, and the model does not implement one cell that is decided (row 28). For these cases,
  PLAN's "One intentional difference… Every other end state… is Manim's"
  (`PLAN.md:184-188`) is false.
- **Evidence** (all PoC 4 model, Manim 0.21):
  - **`Homotopy` that ends away from its start.** A `Homotopy(h, curve)` that ends one unit
    up moves a plain `VMobject` by 1.0 and the bound artist by 0.0 (E6). The artist has no
    Transform target, so resume rebuilds it and the end state is discarded. The artist matrix
    has no non-returning, non-Transform animation (`poc4/test_animations.py:77-89`).
  - **`curve.reverse_points()` does nothing.** The first point stays at x = −3.0, so `Create`
    still draws left to right (E7). `mobject.py::Mobject.reverse_points` (`:1549-1552`)
    writes through `apply_over_attr_arrays`, so there is no writer frame to read.
    `make_smooth`, `change_anchor_mode`, `insert_n_curves` and `set_points` take the same
    path (`vectorized_mobject.py`, `:1199`, `:1165`, `:1897`, `:796`); this is read from
    the code, not measured.
  - **A detached artist moves twice.** `VGroup(curve, Dot()).shift(RIGHT)` moves a detached
    artist by 2.0 (E8): Manim writes the buffer, then `capture` applies the shift a second
    time (`poc4/model.py:618-624`, `:809-810`).
  - **A curve animated during an axes animation lags, then jumps.** During
    `ax.animate.shift(2 * RIGHT)`, `Indicate(curve)` and `curve.animate.set_color(RED)`
    leave the curve at dx 0.0 in every frame while the axes reach 1.78. The curve then jumps
    to 2.0 at the end. `Create(curve)` follows the axes in every frame (E9). The cause is
    the order inside `transform.py::Transform.begin` (`:204-212`). `align_data` marks both
    the live leaf and `target_copy` as transient (`poc4/model.py:686-693`). The starting
    copy is taken after that, in `Animation.begin`, so it inherits the flag. Both copies
    therefore freeze, while `Create`'s starting copy, taken before any suspension, stays
    live.
  - **Copies are registered.**
    - One `play(Create(curve))` leaves two registered artists: the starting copy stays
      alive in `scene.animations`.
    - `curve.copy()` makes it three.
    - A copy taken mid-animation keeps `_transient=True` and does not follow `ax.shift(UP)`:
      it moves 0.0, the original 1.0 (E10).

    PoC 1 asked ADR 0001 to state who owns a clone (`docs/poc-points-property.md:284-290`).
    No document does, and F-801 "collects the registered artists".
  - **A plain target freezes the curve.** After `Transform(curve, Circle())` the curve is
    detached, and `ax.shift(RIGHT)` moves it by 0.0 (E11). PLAN rule 3 says it is "kept in
    system-local coordinates" (`PLAN.md:152-153`).
  - **`ReplacementTransform` does not rebind.** `ReplacementTransform(ax, new_ax)` must
    rebind the artists to `new_ax` (D20 at `docs/grill-log.md:566`; F-708). PoC 4 measured
    "binding transfer absent" (`docs/poc4-keyed-alignment.md:162`, `:420`), and so does E12.
    No entry in the stack contract covers detecting the replacement.
  - **`become` between systems.** `a.become(b)` between two keyed systems keeps
    `a.x_range` at (−3, 3) and duplicates ticks (E13). `always_redraw(lambda: mp.Axes(...))`
    is therefore undefined.
  - **Inactive pool leaves enter bounds.** In the first frame of
    `ax.animate.set_x_range((0, 20))`, `ax.get_center().x` is 8.5 while the visible leaves
    centre on 0.0 (E14). F-914 keeps the frame out of bounds and pivots; nothing does the
    same for the pool.
  - **Undefined, not measured:**
    - nested or concurrent suspensions of one leaf (a single boolean at
      `poc4/model.py:650`, `:673`, while the frame keeps a list at `:145`, `:165-167`);
    - `refresh()` and `become()` inside an animation (both clear the transient state,
      `:719-723`, `:741-746`);
    - points that introducers capture in their constructors (open in ADR; PoC 4 patches
      `GrowFromCenter` by class at `:630-632`).
- **Fix.** Put the table of section 5 into ADR §4, decide every `?` cell, and extend
  F-906's matrix with one test each for:
  - a non-returning, non-Transform animation on an artist;
  - an artist animation running at the same time as a permanent system animation;
  - `copy()` in every state;
  - a container moving a detached artist;
  - `reverse_points` and `make_smooth`;
  - `become` between two systems;
  - bounds during a keyed animation.
- **Cost.** One ADR page, about ten decisions and eight tests. The `ReplacementTransform`
  rebinding needs a mechanism, or a move to 0.2.

### Blocker 4. F-917's pins cannot pass on both supported versions

- **Problem.** F-917 pins "every Manim frame, local and line" by source hash
  (`docs/scope.md:216`, `PLAN.md:169-172`). F-1007 supports both 0.21 and 0.22
  (`docs/scope.md:229`). One pin set cannot match both.
- **Evidence.**
  - *AST comparison* of the 68 PoC 4 pins (E19). All 68 match 0.21.0. In 0.22.0, 28 first
    lines moved, for example `Mobject.shift` 1262 → 1382,
    `Mobject.apply_points_function_about_point` 1569 → 1689 and `Scene.update_to_time`
    1700 → 1714. Two bodies changed: `Scene.get_moving_mobjects` and `CairoRenderer.play`.
  - *The PoC 4 suite on 0.22.0* (E20). 228 tests pass and 68 fail. Every failure is
    `test_k1_cited_manim_symbol`, on `assert '0.22.0' == '0.21.0'`
    (`poc4/test_manim_contract.py:14`).
  - *The version range.* F-1007's "0.21.x and 0.22.x" and `manim>=0.21,<0.23`
    (`pyproject.toml:20`) also admit patch releases nobody pinned. ADR 0001 says supporting
    a new version is "a review step, not a version-range bump"
    (`docs/adr/0001-architecture.md:245-249`).
- **Fix.**
  - F-917 keeps one pin table per supported Manim version.
  - Pin each symbol and the hash of its body, and derive line numbers at import, as PoC 4
    already does (`poc4/context.py:32-52`).
  - F-1007 names exact versions, or the package checks the frame hashes at import and
    refuses or warns on a version it has not pinned.
- **Cost.** Two sentences in scope and a small change to the test.

### Blocker 5. The tick pool's schedule is unspecified, and the proposed fix reproduces a measured bug

- **Problem.** Finding 4 of the arch-crew review proposes sampling `run_time × frame_rate`,
  read from the animation on the stack (`docs/architecture-review-2026-10-24.md:88-91`).
  PoC 4 does exactly that (`poc4/model.py:376-384`). Three things break it:
  - *Compositions.* Inside a composition, a child's `run_time` is not its rendered duration.
    `composition.py::AnimationGroup.interpolate` (`:162-191`) maps group time through the
    group's rate function.
  - *Render times.* Frames are rendered at `np.arange(0, run_time, 1/fps)`
    (`scene.py::Scene.get_time_progression`, `:1101`), not at the PoC's
    `linspace(0, 1, n + 1)`.
  - *Unstable keys.* ADR Q3 makes the key of `MaxN` "relative to the current range"
    (`docs/adr/0001-architecture.md:269-274`). A union of keys over a parameter path cannot
    use keys like that.
- **Evidence.** Pan a `Multiple(1)` axis from (−3, 3) to (97, 103) inside
  `AnimationGroup(..., run_time=3)`. The pool takes 16 samples for 45 rendered frames, and
  14 of those frames show active ticks that have no leaf, up to six at once. Played directly,
  the same animation takes 46 samples and misses none (E17).
- **Fix.** Specify:
  - the pool as the union over the alphas actually rendered, computed from the composition
    tree, or else an open pool, where a key first seen at render time gets a leaf and fades
    in;
  - keys that stay stable across ranges;
  - what happens to a late key: raise in tests, fade in during production.
- **Cost.** One paragraph, and one test per composition type.

### Blocker 6. The public `Source` protocol names types nobody defined

- **Problem.** ADR §3 freezes `Source.sample(map: CompiledMap, bounds: Bounds) -> Payload`
  and `at(t)` (`docs/adr/0001-architecture.md:176-187`).
  - `CompiledMap` and `Bounds` appear nowhere else.
  - `CompiledMap` is built from `Node`, which is not public in 0.1 (Q1, `:262-265`).
  - F-710's `Morph` needs `resample_like` (`docs/grill-log.md:210`), and the protocol does
    not have it.
  - F-707's `i2gp` needs `at(t)`, but no document says what `at(t)` means for an array or
    scatter source.
- **Evidence.** A search for `Bounds|CompiledMap|resample_like` over ADR, scope, PLAN and
  the grill log finds only the signature line and D8.
- **Fix.** Either declare `Source` internal in 0.1, as `Node` is, or define both types and
  both methods. If `Bounds` stays public, it must admit a non-rectangular viewport.
  Otherwise polar, whose viewport is a disc, changes it in 0.2.
- **Cost.** One sentence if `Source` becomes internal, half a page otherwise.

## 3. Findings

### A. Architecture

**A1 — major. The frame's fast path needs SciPy, which the core may not import.**
- *Evidence.* ADR §1 allows the core "NumPy and the standard library and nothing else"
  (`docs/adr/0001-architecture.md:33-34`). ADR §4 and finding 3 of the arch-crew review put
  the frame map in the core. PoC 4's bilinear path passed the gate at 3.73 ms p95, mapping
  through `scipy.sparse.csr_matrix` (`poc4/model.py:11`, `:247-260`). For 32 k control
  points, `csr_matrix` takes 0.14 ms; three NumPy-only gathers take 1.40, 2.73 and 3.77 ms
  (E18).
- *Fix.* Allow SciPy in the core (Manim already depends on it), or re-measure F-1001 with
  the NumPy path.

**A2 — major. More of the mechanism is pure than ADR §2 puts in the core.**
- *Evidence.* Besides the frame numerics (finding 3 of the arch-crew review), these are
  functions of numbers and can be property-tested without a mobject:
  - the pool plan — keys, presence and opacity envelope, computed from the locator, the
    parameter path and the alpha schedule (`poc4/model.py:371-411`);
  - the lifecycle's transition function (state, event → state, actions);
  - the permanence comparison (`:195-199`);
  - composition of an artist's own transform: conjugation `F⁻¹∘G∘F` and affine collapse
    (`:808-839`);
  - densification of sparse leaves (`:527-542`);
  - label overlap layout from label boxes.

  These must stay on the Manim side: the `points` property, the overrides of suspend,
  resume and `align_data`, the stack reads, the rewriting of `starting_mobject` and
  `outline`, the deepcopy hooks, the simulation and the submobject surgery.
- *Fix.* Name modules for the pure parts in ADR §2.

**A3 — major. The lifecycle state machine:** see blocker 3 and section 5.

**A4 — major. The stack contract on 0.22:** see blocker 4 and section 6.

**A5 — the contracts, checked against the planar frame and the native data channel.**

The paper checks of `docs/scope.md`, redone for a planar 2D frame and for data parameters
interpolated under `.animate`:
- *Date and time axes: fit.* The range interpolates linearly in float epoch. The pool needs
  keys that stay stable across ranges (blocker 5), and `(year, month)` keys do. When the
  locator changes level, say from months to years, two keys sit at one position and the
  pool cross-fades them; that should be specified. Labels: see the first minor item below.
- *The calculus toolkit: fits.* `i2gp` goes through `Source.at`, the map and the frame. It
  is exact on an affine frame, and on a non-affine one it inherits the approximation D18
  records. Riemann animations of the form `Transform(rects, …)` would need keyed alignment
  of an artist's family; D21 aligns systems only. That is new work, not a breaking change.
- *Region sampling: fits.* The frame maps local coordinates to the scene point by point.
  Under a non-affine frame the straight edges of a cell need the densification that F-914
  grants only to "sparse derived leaves". Extend the rule when regions arrive; this is not a
  breaking change.
- *An independent second scale (F-610): fits.* A second `Map` shares the frame. Pool roles
  need an axis component, which is internal.
- *Polar: fits,* through a non-separable `Node`, which is internal until 0.2, provided
  `Bounds` is fixed (blocker 6).
- *3D: needs a different frame.* See the second minor item below.

Scale, Locator and Formatter themselves hold at protocol level in every case.
- **minor — labels carry no hint for the renderer.** `Labels.text` is LaTeX in math mode only
  (ADR §3, `:162-165`). The renderer has two paths, a glyph cache for numerals and a whole
  `MathTex` for anything else, and `Labels` does not say which one to take. A date
  formatter's "Jan 2020" is neither numeric nor fixed at configuration, so every new string
  compiles TeX inside a frame, at 0.2–0.5 s each (`docs/poc-points-property.md:374-379`).
  *Fix:* a text-mode flag, or a kind per label. It costs nothing now.
- **minor — 3D needs a different frame.** D15 says "3D needs no change to the model"
  (`docs/grill-log.md:459-460`). D18's planar frame cannot carry scaling off the plane
  (`docs/poc3-stack-context.md:34-37`). This is not a break of a public contract. *Fix:*
  record that 3D replaces the frame's representation.
- `Source`: see blocker 6.

**A6 — major. F-1001 is no longer well defined after D18-D21, and the largest new costs fall
outside it.**
- *Undefined.* The requirement leaves open:
  - what "rebuild" includes: callable sampling, pool configuration, label layout, the
    frame's `check()` and the stack reads;
  - what "2 000 samples" means under adaptive sampling (F-704);
  - which frame path is measured;
  - which parameter is animated (a tracker changes no ticks, a range does);
  - the calling convention (blocker 1).
- *Outside the gate, measured:*
  - *Lost static background.* F-915's updaters make Cairo redraw everything every frame. An
    unrelated dot animation over axes and four curves at 1080p60 goes from 2.2 to
    12.9 ms/frame (E15).
  - *Container operations.* They grow quadratically in PoC 4.
    `VGroup(ax, *curves).shift` costs 1.45, 31.5, 229 and 914 ms for 13, 103, 303 and 603
    system leaves; plain Manim takes 0.03–0.98 ms (E16). The cause is a `get_family()`
    membership test on every write (`poc4/model.py:605`, `:614-615`).
  - *The classifier.* It costs 6.6 ms median per system animation, and 39–41 ms inside
    compositions (`docs/poc3-stack-context.md:214-222`).
  - *`align_data`.* It costs 12.7 ms for a 601-sample pool
    (`docs/poc4-keyed-alignment.md:357-359`).
  - *Scalar evaluation.* It adds 1.1–1.7 ms per frame (E3).
- *Fix.*
  - Gate `Scene.update_to_time` end to end, plus the camera's lazy rebuilds (rasterisation
    excluded). Run it on both frame paths, with labels and an animated range.
  - Add a second gate: a static plot under an unrelated animation, measured relative to
    plain Manim.
  - Require writer membership to be memoised per operation.
  - Narrow F-915 to the system and each artist. That is enough, because
    `scene.py::Scene.get_moving_mobjects` (`:937-946`) checks family updaters.

**A7 — an assessment of the arch-crew review (`docs/architecture-review-2026-10-24.md`).**
- *Finding 1 (seam rule) is right, but the proposed test is too narrow.* The model's
  coupling outside `context.py` goes through public-but-internal attributes and overrides:
  - It assigns `animation.starting_mobject`, `animation.outline` and `animation.point`
    (`poc4/model.py:630-635`).
  - It reads `animation.run_time`, `rate_func` and `config.frame_rate` (`:376-380`).
  - It overrides `pointwise_become_partial`, `set_fill`, `set_stroke`, `interpolate_color`
    and `get_anchors` (`:203-223`). Only the last of these is pinned
    (`poc4/evidence.py:35-104`).

  The table row "everything else uses public Mobject methods" (`:23`) is therefore wrong.
  *Fix:* list in F-917 the Manim methods the library overrides and the animation attributes
  it assigns.
- *Finding 2 is right.* It is blocker 3.
- *Finding 3 is right.* Add A1 (SciPy) and A2 to it.
- *Finding 4 is right, but its first step reproduces E17.* See blocker 5.
- *What the review misses:* blockers 1, 2, 4 and 6, the render cost of F-915, and the
  semantics of copies and the registry. Its least-architecture check (`:26-32`) names only
  the non-affine frame; section 7 lists more.

### B. Compatibility with Manim

**B1 — major. NumberPlane, ComplexPlane and NumberLine have no counterpart and no verdict.**
- *Evidence.* Ten of the 48 corpus scenes use `NumberPlane` or `ComplexPlane`, and two use
  a standalone `NumberLine`. Three plot on a `NumberPlane`: `DerivativeGraphExample` (`:1529`),
  `LineGraphExample` (`:2347`) and `DiscontinuousExample` (`functions.py:87`). Scope names
  these classes only as things not to subclass (`docs/scope.md:379-380`). F-1009 arguably
  already requires them, since `NumberPlane` is `Axes` plus a grid, which is F-607.
- *Fix.* Give each class a tier, and say whether F-607's grid on top of the `mp.Axes`
  defaults reproduces `NumberPlane()`.

**B2 — major. `plot`'s Manim keywords have no requirement.**
- *Evidence.*
  - D2 promises `t_range`, `discontinuities`, `use_smoothing` and `use_vectorized`
    (`docs/grill-log.md:28-32`), but scope has none of them.
  - `CoordinateSystem.plot` also takes `colorscale` and a step in `x_range` (`:733`).
  - The corpus uses `use_smoothing=False` (three scenes), an `x_range` with a step
    (`PlotExample`), and `discontinuities` with `dt` (`DiscontinuousExample`).
  - Defect 15a rests on a wrong premise, "plot() has no `discontinuities` parameter"
    (`docs/defect-audit-0.21.md:291`). `plot` forwards its kwargs to `ParametricFunction`
    (`:738-744`), which takes both (`functions.py:111-112`).
- *Fix.* One requirement per keyword. Each is either honoured, translated (the step becomes
  a minimum sampling density, `discontinuities` become forced splits) or rejected by name.

**B3 — major. F-705 cannot split at a pole that no sample hits.**
- *Evidence.* PLAN calls `ax.plot(lambda x: 1/x)` a day-one case (`PLAN.md:265-270`), but
  F-705 splits only on NaN, ±inf or a domain violation. An adaptive sampler rarely lands
  exactly on 0. The samples either side are finite, and F-706 then clips the segment joining
  them to a vertical line across the plot. PoC 2 tested path mechanics, "not pole detection"
  (`docs/poc2-frame-lifecycle.md:320-322`).
- *Fix.* Give the sampler a divergence criterion (a sign change with a magnitude growing past
  the viewport), plus `discontinuities=`.

**B4 — major. `ax.x_axis` must also speak NumberLine.**
- *Evidence.* F-602 makes `ax.x` and `ax.x_axis` the same object, and F-603 gives it
  `ticks.major` and `labels`. In Manim, `x_axis.ticks` is a VGroup of Lines
  (`number_line.py::NumberLine.add_ticks`, `:287-302`), and `x_axis.labels` holds the

### E. Test strategy

**E1 — major. Nothing tests the result against Manim's own `Axes`.**
- *Evidence.* D17's promise that swapping the class keeps the picture has no test. The
  differential oracle compares artists with plain `VMobject`s, and systems with our own
  frame-free hierarchy, "not Manim's `Axes`" (`docs/poc3-stack-context.md:532-536`).
- *Fix.* A geometry-level parity test. For every corpus scene and every idiom in section 4,
  build `Axes(...)` and `mp.Axes(...)` with the same arguments. Compare tick positions,
  label strings and positions, axis line endpoints and curve samples, modulo the differences
  F-1008 records. The corpus thereby becomes executable.

**E2 — major. The ported PoC tests are not independent oracles.**
- *Evidence.* PoC 3 (K6) and PoC 4 ("Changed copied expectations") rewrote expectations
  together with the model. For example, they "stop requiring the live-data oracle after
  detachment" and accept "PhaseFlow has more than one node"
  (`docs/poc4-keyed-alignment.md:382-384`). The rows for non-linear system animations use,
  as their oracle, a bilinear interpolant over the same grid
  (`docs/poc2-frame-lifecycle.md:144-146`; `poc4/test_animations.py:40`): they check the
  interpolation, not what the user sees. The arch-crew review's "their tests compare against
  independently computed references" (`:147-151`) overstates.
- *Fix.* Tag each ported test as either a decision regression or a correctness oracle. A
  correctness oracle must be plain Manim or analytic.

**E3 — major. Several risks have no row of evidence.**
- *Evidence.* Nothing in the portfolio covers:
  - late binding (E1) and the calling convention (E2, E3);
  - the render cost of F-915 (E15) and the growth of container operations (E16);
  - copies (E10);
  - the end state of `Homotopy` (E6);
  - concurrent animations of an artist and its system (E9);
  - the pool inside compositions (E17);
  - caching, which every PoC turned off (`poc4/conftest.py:19`).
- *Fix.* Add one row per risk.

**E4 — major. The contract row cannot pass on 0.22.**
- *Evidence.* The row says "symbol, first line and source hash … rerun per supported version"
  (`:142`). It cannot pass on 0.22 (E19, E20). The animation matrix had also never run on
  0.22: `tools/check.py:45-47` runs `pytest`, whose `testpaths` cover only `tests/`
  (`pyproject.toml:86`).
- *Fix.* Keep one pin set per version, and run the matrix on both versions.

**E5 — minor. Some rows are more than needed.**
- *Evidence.* Two rows ask for more than the requirements support. One is the relative
  baseline: the benchmark keeps "one machine-specific baseline per machine", but no
  comparable baseline exists. The other is "one test per non-empty cell" of a table that
  does not exist yet.
- *Fix.* Defer the relative gate. Derive the matrix once blocker 3 exists.

## 5. Lifecycle: states × events (A.3)

- **A** — attached and live.
- **F** — attached, reading a frozen frame: an impermanent system animation is running and

- **R** — detached by a remover.
